# Pi 1.2.0 comparison and Alloy adoption review

Date: 13 October 2026. Scope: source audit and offline behavioural checks; no production implementation, PR merge, or publication.

## Implementation follow-up

The original findings below describe the audited snapshots, not the subsequent
working-tree changes. The first implementation batch on the local 0.12.5 branch:

- Removes thinking and redacted thinking from summary input, covering atom and
  string keys, without stripping live provider input.
- Classifies subscription-sharing exhaustion as quota rather than throttling.
- Parses HTTP-date `Retry-After` and exercises it through the existing deadline
  guard. Past dates become zero delay; malformed dates retain ordinary backoff.
- Adds regression coverage preserving visible decisions and tool evidence.

The initial regression run reproduced three failures before the fixes; the
targeted suite then passed 98 tests. The subsequent implementation adds typed
malformed-reply recovery (#55), opt-in Codex continuation and clean structured
reply streaming (#56), and tested host-only experiments for #54/#57. Broad
message-text heuristics are not added without provider fixtures; #58 remains
deferred. See [implementation verification](VERIFICATION-pi-implementation.md)
for the completion matrix, reproducible checks, limits, and external release
steps. Local implementation is not a publication or a production deployment.

The [minimal-core ADR](adr/0001-minimal-core-and-optional-capabilities.md) records
the agreed boundary; it does not introduce a new execution API.

## Conclusion

Pi still describes itself as a minimal, extensible harness. Its overall product and monorepo have grown, but its agent-core package became smaller in 1.0: the experimental harness, sessions, storage, compaction, and durable runtime were removed from that package. Minimalism now needs to be assessed at the package boundary, not by counting everything in the monorepo.

This supports Alloy's 0.13 direction. Borrow protocol fixes, execution invariants, and test scenarios. Keep scripting, output storage, discovery, and durable sessions outside the loop. John's PRs supply useful real-world failure cases; their current patches need not define our architecture.

The strongest immediate candidates are excluding thinking from summary input and improving structured error classification. Code mode is worth an application experiment only if its nested calls retain the ordinary execution safeguards. Publishing the existing releases remains a prerequisite to treating 0.13 as the consumer baseline.

## Has Pi abandoned minimalism?

No at the agent-core boundary; the application has become more capable.

- [Pi's release README](https://github.com/earendil-works/pi/blob/v1.2.0/README.md#pi) retains the minimal-harness framing and leaves sub-agents and plan mode to customization.
- [Agent-core's 1.0 change](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/CHANGELOG.md#100---2026-10-01) explicitly removes the experimental harness and durable/session features.
- [Agent-core exports](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/index.ts) expose the agent, loop, proxy, stream configuration, and types. Its package depends directly on pi-ai and TypeBox, not on the coding application or durable runtime.
- Code mode has a separate sandbox package and a coding-agent extension; nested-call orchestration lives in the coding application. This is not evidence that a scripting runtime belongs in every consumer's agent loop.

Alloy is not identical to Pi: Alloy includes provider adapters in the same package and retains a default compaction middleware in 0.13. Preserve useful existing boundaries rather than pursuing structural parity for its own sake.

## Ranked changes to consider

### 1. Exclude thinking from the summary request — adopt in compaction middleware

**Verified gap on main and 0.13.** Alloy explicitly serializes assistant thinking into the summary prompt. Removing stale thinking from retained history happens later, in `finalize/2`; it does not reduce the already-issued summary request. Pi 1.2.0 omits thinking from summary serialization, retaining visible text, calls, and results.

Concrete case: a long reasoning-heavy conversation needs compaction, but the summarizer receives that reasoning again. This adds avoidable input and can undermine recovery from context overflow. An offline probe confirmed the thinking marker in Alloy's actual summary request on both snapshots. The ordinary thinking signature was not included; the initial test assumption that it was exposed was corrected.

Sources: [Alloy serialization, line 816](https://github.com/alloy-ex/alloy/blob/32447cdc807ea491b124aa7861f34e3c7f369577/lib/alloy/context/compactor.ex#L816), [Alloy finalization, line 254](https://github.com/alloy-ex/alloy/blob/32447cdc807ea491b124aa7861f34e3c7f369577/lib/alloy/context/compactor.ex#L254), [Pi serialization, line 114](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/compaction/utils.ts#L114).

Acceptance tests: summary input excludes thinking, redacted thinking, and opaque reasoning; visible decisions and tool evidence remain; summary usage accounting, tool-round boundaries, and the existing stale-signature tests still pass. Do not remove live provider reasoning indiscriminately.

### 2. Improve retry classification — adopt narrow, fixture-backed cases

**Verified differences, not a reason to copy Pi's broad regex wholesale.** Offline checks showed:

- An in-band error containing only `The upstream provider returned an error` becomes `:unknown` in Alloy and is not retried.
- A 429 with `subscription_sharing_usage_limit_exceeded` becomes retryable `:rate_limited`, although Pi excludes that long-lived subscription exhaustion from transient retries.
- An HTTP-date `Retry-After` is ignored; only numeric durations are parsed.

These are input-shape checks, not live evidence that every Alloy provider currently emits them. Ordinary HTTP 5xx already retries correctly. Apply label mappings and narrowly scoped provider fallbacks where fixtures justify them, retaining Alloy's useful structured `%Provider.Error{}` contract and no-retry-after-streamed-output rule. Do not classify arbitrary messages containing a number or the word billing solely by substring.

Sources: [Alloy classification, line 186](https://github.com/alloy-ex/alloy/blob/32447cdc807ea491b124aa7861f34e3c7f369577/lib/alloy/provider/error.ex#L186), [Alloy Retry-After, line 229](https://github.com/alloy-ex/alloy/blob/32447cdc807ea491b124aa7861f34e3c7f369577/lib/alloy/provider/error.ex#L229), [Pi retry policy](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/utils/retry.ts), [Pi transport retry](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/utils/provider-retry.ts).

Acceptance tests: distinguish quota from transient throttling; honor HTTP-date without exceeding the run deadline; retain bounded attempts; never repeat a request after answer chunks were delivered.

### 3. Route nested calls through ordinary execution — prerequisite for code mode

**John #57 needs more than documentation wording if hosts rely on middleware.** Its recipe invokes each nested module's `execute/2` directly. The outer `run_script` receives normal middleware and a timeout, but nested calls miss the ordinary per-tool validation, middleware, and event path.

Pi's code-mode extension calls `ctx.executeTool`. The coding session routes that through the shared `runToolCall` primitive, with before/after hooks and a cancellation signal; the surrounding runner emits nested events and tracks parent identity. This is the valuable pattern to borrow, independent of JavaScript versus Lua.

Sources: [John's direct call, line 93](https://github.com/alloy-ex/alloy/blob/d01bc058e367b8b7262ccdc333a7099b40fe4c56/docs/recipes/code-mode.md#L93), [Pi code-mode dispatch, line 485](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/extensions/codemode/execute.ts#L485), [Pi session dispatch, line 727](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/agent-session.ts#L727), [Pi reusable execution, line 802](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/agent-loop.ts#L802).

Suggested application experiment: one script tool, explicitly supplied callable tools, host-owned context, and a dispatcher that reuses Alloy's existing execution path. Extract a small reusable executor primitive only if the experiment demonstrates that the existing API cannot express this cleanly. Keep the language VM, discovery, and script state outside Alloy core.

Acceptance tests: blocked nested writes never execute; cancellation stops active and pending children; sequential tools remain sequential; structured results survive; each nested event has a parent call; recursive script execution is bounded or excluded. Passing context through a closure alone does not preserve all these properties.

### 4. Preserve large output at the producer — application/tool layer

**Keep #54's use case, change its design.** John's executor-level spill sees bash output only after Alloy's bounded head/tail capture has already discarded the middle. It cannot recover full output at that stage.

Pi's bash tool uses an output accumulator during capture, retaining a bounded display tail and writing output to a file when needed. Its shared output-file helper uses random names, exclusive creation (`wx`), and owner-only permissions (`0600`). This directly addresses the predictable-name overwrites and symlink-following reproduced in #54.

Sources: [Pi accumulator](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/core/tools/output-accumulator.ts), [Pi output-file helper](https://github.com/earendil-works/pi/blob/v1.2.0/packages/coding-agent/src/utils/output-files.ts), [John's write path, line 77](https://github.com/alloy-ex/alloy/blob/c5798dd2889f3ed76583797dc92401cb78a41510/lib/alloy/tool/spill.ex#L77).

Implement first through an application-owned bash executor or tool wrapper. The host owns location, retention, tenant isolation, retrieval, and disk quotas. Do not claim bounded total memory merely from a bounded preview: streaming writes also need backpressure. Do not replace Alloy's existing bounded capture with an unbounded buffer just to enable spilling.

### 5. Repair incomplete imported tool rounds — consider at the transcript boundary

**Verified difference in 0.13.** Pi synthesizes an error result for an unanswered call before the next user turn or at transcript end. Alloy's `Message.normalize_for/3` normalizes provenance and IDs but leaves an unanswered call untouched. Offline checks executed both implementations on equivalent interrupted histories.

This matters for application-restored or manually assembled transcripts, not as evidence that Alloy's ordinary successful tool loop loses results. Alloy already protects its own truncated tool-call path.

Sources: [Pi repair, line 167](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/api/transform-messages.ts#L167), [Alloy normalization, line 239](https://github.com/alloy-ex/alloy/blob/32447cdc807ea491b124aa7861f34e3c7f369577/lib/alloy/message.ex#L239).

Prefer an explicit validator/repair boundary for resumed input. Never invent a successful outcome or automatically rerun a possibly side-effecting tool. Tests should cover partial multi-call batches, no duplicate results, interrupted writes, and repeated normalization.

### 6. Strict-tool fallback — conditional provider enhancement

Pi retries a narrowly identified Anthropic grammar-limit rejection once with only tools marked `strict: prefer` downgraded. Tools marked `require` stay strict; fallback occurs before streaming starts. Alloy currently exposes `strict: true`, without that prefer/require distinction.

Therefore, do not silently downgrade Alloy's existing strict tools. Consider this only with an explicit optional preference contract and a concrete consumer requirement. Otherwise improved diagnostics are sufficient.

Sources: [Pi guarded fallback, line 665](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/api/anthropic-messages.ts#L665), [Alloy strict mapping, line 615](https://github.com/alloy-ex/alloy/blob/32447cdc807ea491b124aa7861f34e3c7f369577/lib/alloy/provider/anthropic.ex#L615).

### 7. Catalogs, timing, and image capability — optional follow-ups

- **Account-specific catalogs:** Pi's 1.2 OpenRouter refresh uses the actual key's catalog. An Alloy `ModelCatalog` adapter is the appropriate boundary. Do not build account login, catalog persistence, or model selection policy into the loop.
- **Tool timing:** Pi distinguishes execution time from hooks; Alloy's `duration_ms` includes queue wait. Preserve existing semantics. If operators need both, add separately named execution and queue metrics rather than silently changing duration.
- **Non-vision fallbacks:** Pi replaces images with explicit placeholders for text-only models. An offline check verified that transformation. For applications that depend on drawings or images, an explicit incompatibility error may be safer than dropping the evidence. Treat this as caller policy, not an automatic parity change.

Sources: [Pi catalog release notes](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/CHANGELOG.md#120---2026-10-12), [Pi execution timing, line 828](https://github.com/earendil-works/pi/blob/v1.2.0/packages/agent/src/agent-loop.ts#L828), [Alloy timing, line 306](https://github.com/alloy-ex/alloy/blob/32447cdc807ea491b124aa7861f34e3c7f369577/lib/alloy/tool/executor.ex#L306), [Pi image transformation, line 35](https://github.com/earendil-works/pi/blob/v1.2.0/packages/ai/src/api/transform-messages.ts#L35).

## What Alloy already does well

Do not reopen solved work merely to resemble Pi:

- Truncated tool arguments are not executed; Alloy adds error results to preserve the transcript (`agent/turn.ex`, `abandon_truncated_tool_calls/2`).
- Provider errors are structured, backoff is bounded by a deadline, and emitted streaming output prevents ordinary retry/fallback duplication.
- 0.12.5 bounds bash capture, kills process groups on timeout, restricts inherited secrets, and tightens path handling.
- 0.13 already normalizes cross-origin history and tool IDs, and treats compaction and memory through middleware/tools.
- Existing tool concurrency and cancellation supervision should remain the foundation of nested execution.

Pi's model-switch rule is not identical to Alloy's: Pi compares provider, API, and model, while Alloy 0.13 tracks provider/account/endpoint origin and deliberately allows same-origin model changes. Do not overwrite this recent design without provider-specific evidence and regression tests.

## Delivery order

1. Complete the existing release chain: publish the tested 0.12.5 baseline, resolve the alloy_agent release prerequisites, then integrate and publish 0.13 in a consumer-safe order. PR #52's merged badge does not mean its code is on main.
2. Make separate small fixes for compaction summary input and justified retry classifications. Include fixtures and full existing relevant tests.
3. Build an application-level code-mode/output-capture experiment. Demonstrate authority checks, cancellation, output retrieval, and bounded resources before creating new core API.
4. Add provider continuation only after testing it through the full 0.13 loop, not just direct provider calls. Do not hash metadata that the loop adds afterward.
5. Reassess whether a maintained Claude CLI adapter is worth its surface area. Defer strict-preference API, expanded catalogs, and richer runtime features until required.
